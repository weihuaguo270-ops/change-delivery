# P2 范围说明 — Go 服务侧（已冻结口径）

> 冻结日：2026-11-15（Asia/Shanghai）。  
> **本刀只定范围，不写 Go 代码、不选实现模块落地。**  
> 上位边界：[SCOPE.md](SCOPE.md)。P1 仍为 mock / 原型 complete，见 [P1_ACCEPTANCE.md](P1_ACCEPTANCE.md)。

## 1. P2 要解决什么

把 P1 已证明的主路径（Issue → shadow → 钉死 `plan_sha256` 的审批 → Draft）接到**可运营的服务侧外壳**：收事件、排队、落状态、调 GitHub API。  
Agent 计划 / 影子执行 / 审批语义仍留在现有契约与演示边界内，**不用 Go 重写 Agent 循环**。

## 2. Go 只做的四块（服务侧）

| 模块 | 职责 | 明确不做 |
|---|---|---|
| Webhook 与鉴权 | 接收 GitHub（或等价）事件；校验来源签名 / 信任边界；映射为内部任务意图 | 在 webhook 里跑模型或 `react_loop` |
| 任务队列 | 异步投递、重试、幂等键；把「该跑 shadow / 该开 Draft」排进队列 | 用队列代替人工审批或绕过 `plan_sha256` |
| 状态持久化 | Episode / Artifact / 审批绑定 / PR 状态的持久存储与查询 | 把轨迹运行时或权限内核搬进 Go |
| GitHub API | 受控创建 / 更新 Draft PR、同步 PR 状态；外部写仍需显式授权 | 无审批或指纹不一致时仍写仓库 |

四块是**范围清单**，不是一次交付包。范围过关后**只选其中一个最小模块**实现；其余保持文档预留。

## 3. 硬约束（与 P0/P1 对齐）

- **不重写 Agent 循环**：禁止 Go 实现 `react_loop` / ToolGuard / 轨迹记录内核。
- **不一次铺开**：本阶段禁止同时开工四块或上常驻多租户生产壳。
- **审批钉死指纹**：服务侧开 Draft 前必须校验审批记录与当前 `plan_sha256` 一致；不一致则拒绝并要求重新 shadow + 审批。
- **身份不从 body 授权**：延续 `X-Actor-Id`（或网关注入的等价信任头）→ 服务端构造 Actor。
- **不迁工作助手代码**：不从 `react-agent` 搬循环或仓库结构；只对齐契约。
- **工作助手交付附录保留**：`react-agent/docs/features/github-delivery-workflow.md` 等附录**先保留**作历史 / 只读参考，本刀不删、不迁、不改称为本仓已交付能力。

## 4. 过关后如何开下一刀（实现）

范围人工确认后，另开刀时按下列顺序**只挑一项**作为最小模块（其余不动）：

1. **优先候选**：Webhook 与鉴权（空壳收事件 + 验签 + 拒绝伪造）— 边界清晰、不碰 Draft 写入  
2. 或：状态持久化（审批 / `plan_sha256` / run 状态落库，仍无真实 GitHub 写）  
3. 或：任务队列（入队 / 幂等 / 重试，worker 可先 no-op）  
4. 最后才考虑：GitHub API Draft 写入（必须已有指纹校验与显式 `allow_external_write`）

选定模块时另写该模块的验收口径；**不得**在范围冻结刀顺手写代码。
